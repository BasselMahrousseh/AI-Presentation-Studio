# AI-Presentation-Studio

## Working with this user

The user is an MIS (Management Information Systems) student with some coding ability but limited background in software engineering, APIs, and LLMs — and wants to actually learn these concepts over time, not just get them hidden. When explaining technical concepts, findings, or decisions, keep it plain and systematic — one or two sentences per point rather than long technical prose — but still introduce and briefly explain the relevant term or concept rather than skipping it entirely.

## Origin

This repo is a fork of the open-source presentation generator from **presenton.ai** — the Next.js `package.json` name is still `presenton`, and much of the generic branding/module naming traces back to that upstream project. The team is incrementally layering custom features and branding (an "e&"/Etisalat-branded smart-deck mode, UI reskins, etc.) on top of that inherited base rather than building from scratch. When something looks orphaned, duplicated, or inconsistently named, check whether it's inherited upstream functionality that predates the e&-specific work before assuming it's a local bug.

Working branch: `restructured-v3-branch`, created off `restructured-v3`. See pinned memory for the git workflow rule (never commit/push directly to `restructured-v3`).

## Architecture

Two servers: `servers/fastapi` (backend, :8000) and `servers/nextjs` (frontend, :3000), talked to by the browser through `proxy.ts` (a Next.js "Proxy," the v16 rename of middleware) which rewrites `/api/v1/*` and `/api/v2/*` to FastAPI.

**Two parallel slide-content models — know which one you're in before changing generation code:**
- **TemplateV2 (structured)**: slides are JSON — a `content` object plus a `ui` element tree (`text`, `image`, `chart`, `table`, `text-list`, `flex`, `grid`, ...), schema-constrained per layout. Bundled templates live at repo-root `/templates/*/template.json`, seeded into the `template_v2` SQL table on startup. Rendered via `lib/template-v2-json-to-html.ts` (flat HTML) or a Konva canvas editor (`components/slide-editor/*`) for drag/resize editing. This is the **"standard"** generation path (`stream_presentation`, `?type=standard`) — each slide is its own sequential LLM call, so it genuinely streams slide-by-slide.
- **Smart HTML (raw)**: the LLM outputs a Tailwind `<section>` fragment per slide directly, rendered via `SmartHtmlSlide.tsx`'s iframe + browser-side Tailwind runtime (`lib/tailwind-browser.ts`). No schema, no structured editor — editing happens via the in-editor AI chat rewriting raw HTML (feature exists but its toggle button is commented out in `PresentationHeader.tsx`, so it's not discoverable). This is the **"smart"** path (`_stream_smart_presentation`, `?type=smart`) — for reasoning models the whole deck is typically one LLM call that "thinks" silently for a long stretch, then emits all slides in a fast burst. The e& brand template (`smart_brand_templates.py`) is *not* a TemplateV2 template — it's hardcoded literal HTML strings spliced around LLM-generated content.

**The live `/generation` page's button labels don't match this `standard`/`smart` backend terminology — don't infer generation mode from a UI button's label without checking `GenerationPageClient.tsx`.** `/generate` redirects straight to `/generation` (`app/generation/GenerationPageClient.tsx`), which has three actions, none of which is a "pick TemplateV2 vs Smart" toggle: **"Outline"** is the only button that actually sends `generation_mode: "standard"` (real TemplateV2), routing through `/outline` first rather than streaming a deck directly; **"Generate Standard"** is misleadingly named — it sends `generation_mode: "smart"` with no `smart_template` (plain Smart HTML, no e& branding); **"Generate e& deck"** also sends `generation_mode: "smart"`, just with `smart_template: "eand"`. A separate, older mode-picker component (`GenerationModeDialog.tsx` under `(presentation-generator)/upload/`) does correctly present "Standard" vs "Smart" as a real toggle. **Correction to an earlier claim in this file: that page is not dead** — `/generate`'s redirect bypasses it, but `/upload` is independently reachable from four other live entry points (onboarding's "Go to Upload" button, the outline page's empty state, the community page's "New presentation"/"Use this design" actions, and the presentation editor's error-recovery fallback). See the route reachability map below before assuming either `/generation` or `/upload` is "the" generation entry point — this app has two, with different mode-selection UIs.

**e& brand template specifics**: `smart_brand_templates.py`'s `EAND_FIXED_SLIDE_COUNT` (2 — the cover + thank-you slides, spliced in as literal HTML outside the LLM's own output) is *added on top of* the requested slide count, not subtracted from it — `n_slides`/a user's stated count always means content slides only for e& generation. (This was previously backwards — a request for "5 slides" silently produced only 3 content slides — fixed by having `determine_smart_slide_count()`/`resolve_smart_slide_count()` return the content count directly and having the caller in `presentation.py` add `EAND_FIXED_SLIDE_COUNT` for the reported total, instead of subtracting it out.) Content color palette is normally the hardcoded default in `get_smart_brand_prompt()`, but if the user attaches a `.pptx` among their source files when generating an e& deck, `templates/pptx_color_extraction.py` automatically extracts that file's real colors (ranked by actual shape-fill usage frequency across the deck — most real decks, including every deck this app itself exports, never touch their PowerPoint theme colors, so theme-color extraction alone returns generic Office defaults) and uses them instead of the default palette. There's no dedicated upload UI for this; it's inferred automatically from an already-attached file's `.pptx` extension.

The *default* palette (red/dark-blue/white/black, no uploaded reference deck) is deliberately narrow for the rest of the UI, but that narrowness broke charts specifically: a 5+ category pie/bar chart ran out of distinct colors, repeating red and/or using white (which disappears against the white slide/card background). Fixed with a **chart-only** expanded palette block in `get_smart_brand_prompt()` (`CHART COLOR PALETTE` section, explicitly scoped to `<canvas>` configs only — every other element still uses only the 4-color base palette): the base red/dark-blue plus computed 35%-white-tinted shades of each (`_tint_hex()`), plus Etisalat's own pre-"e&" heritage brand green `#82AA40` (with a lighter `#CCDB3B` accent) — independently sourced from the logo-color-extraction site coloropedia.com ("Sushi"/"Wattle"), corroborated by a separate "Lime Green Pantone 381C #CADB2A" reference, since this isn't part of the post-rebrand e& UI palette and needed verifying rather than guessing. This expansion only applies to the *default* palette — an uploaded reference deck's extracted `custom_colors` are left untouched, since those already represent that deck's real brand and shouldn't have invented colors layered on top. Note this is a **prompt-level** fix (steering what colors the LLM picks for `backgroundColor`/`borderColor` when it authors the Chart.js config), not something the post-export pipeline can retroactively correct — by the time `pptx_native_chart_service.py` sees a chart, whatever colors the LLM chose are already baked into both the live in-app preview and the eventual export, so fixing it at the source is what fixes both consistently.

**Smart-mode overflow validation**: `smart_slide_layout.py`'s `inspect_smart_slide_layout()` runs four deterministic, no-rendering heuristics (regex/Tailwind-class analysis via Python's stdlib `html.parser`, not a real layout engine) on every Smart slide before it's accepted, rejecting ones that look likely to overflow and forcing an LLM retry: `_find_shrink_to_fit_overflow_risks` (fixed-height flex-col + `flex-1 min-h-0` + numbered `grid-cols-N≥3`), `_find_shrink_marked_grid_overflow_risks` (broader — CSS's default `flex-shrink:1` means `min-h-0` alone is enough, without needing `flex-1`; also covers arbitrary `grid-cols-[...]` templates and a fixed height implied by `position:absolute` with both `top-*`/`bottom-*` set, not just an explicit height class), `_find_fixed_height_card_text_overflow_risks` (a card's own text length vs. its declared height, width-scaled by the row's column count), and `_find_stacked_list_overflow_risks` (4+ stacked text items in an `h-full`/fixed-height panel). None of these can measure real normal-flow layout — that's structurally impossible without an actual browser — so each is a calibrated proxy, not a guarantee; every one was added after a specific real production slide overflow slipped past the others (verify any new one against real HTML pulled from `app_data/fastapi.db`'s `slides.html_content` before trusting it). Separately, `generate_smart_presentation.py`'s `_check_smart_slide_eand_footer_safe_area` (e&-template-only) actually renders each slide through the Puppeteer-backed export runtime and checks pixels, since the reserved `y≥630` footer zone can't be caught by class analysis at all — the one overflow check in the system that costs real generation latency (a few seconds per e& slide) for a real measurement instead of a heuristic.

**SSE streaming**: `proxy.ts`'s `NextResponse.rewrite()` silently buffers SSE responses (confirmed via direct backend testing — real per-slide gaps at the source, one burst through the browser). The three stream paths (`/api/v1/ppt/presentation/stream/`, `/api/v2/ppt/presentation/stream/`, `/api/v1/ppt/outlines/stream/`) are excluded from that rewrite and instead hit dedicated Route Handlers (`app/api/v1/.../stream/[id]/route.ts`, via `lib/sse-proxy.ts`) that pipe the FastAPI response through untouched. If a new SSE endpoint is ever added, it needs the same treatment or it will silently stop streaming in real time.

**Auth**: session cookie + `sk-presenton-*` API-key bearer tokens, one role bit (`is_superuser`). When `DISABLE_AUTH` is set, the middleware bypasses auth entirely and `/api/v1/auth/status` hardcodes `username: "electron", role: "admin"` — this is a generic single-user bypass mode, not literally tied to the Electron app (which no longer exists in this fork, see below).

**Async jobs**: `AsyncTaskModel` is genuinely used for template creation (polled by the frontend). The equivalent async wrapper for presentation generation (`/generate/async`, `/status/{id}`) is confirmed dead code — nothing in the frontend calls it; the SSE streaming endpoints are what's actually used.

**Single-slide editing**: `POST /api/v1/ppt/slide/edit` (TemplateV2) and `/slide/edit-html` (Smart HTML) are prompt-driven, single-slide endpoints — now used directly by the slide action bar's "Regenerate Slide" button (optional feedback text gets appended to a fixed default prompt), and internally by the AI chat's tool-calling edits. `edit_slide` used to call `presentation.get_layout()` directly, which throws for any presentation whose `layout` column isn't the legacy single-layout shape — most presentations today store either `None` or a `{layouts: [...]}` template-picker payload instead, so this 500 went unnoticed since the endpoint had zero frontend callers before. Fixed via a shared `utils/presentation_layout_resolver.py` (also now used by `services/chat/memory_layer.py`, which already handled both shapes correctly) — any new code needing a presentation's resolved layout should call `resolve_presentation_layout_model()`, never `presentation.get_layout()` directly.

**Generation loading UI**: the header progress pill (`PresentationHeader.tsx`) and the pre-first-slide `OverlayLoader` modal (shown from `PresentationPage.tsx`) both derive their status text from one shared helper, `getStreamProgressLabel()` (`app/(presentation-generator)/presentation/utils/streamProgressLabel.ts`), fed by real SSE-reported `streamTotalSlides`/`streamStageMessage` Redux state — so they can't drift out of sync with each other again. `ProgressBar`/`OverlayLoader` also gained an opt-in `indeterminate`/`indeterminateProgress` mode (an honest "still working" sweep, no fabricated percentage), used only by this modal — the same shared components still default to the old fake elapsed-time percentage for 3 other loading screens (upload, outline, document preview) that weren't touched.

**Export**: neither server renders PPTX/PDF itself — both shell out to the same `presentation-export/` prebuilt Node bundle (Puppeteer-based) as a subprocess, pointed at the live `/pdf-maker` page. That bundle needs the repo-root `node_modules` installed (specifically `sharp`) — **`npm install` at the repo root** (not just `servers/nextjs`) is required and is not mentioned in README's setup steps. If PPTX/PDF export fails with `Cannot find module 'sharp'`, this is why.

**A local Chromium version mismatch makes every Smart-mode render check silently fail open, with no error visible anywhere in the normal flow.** The bundle wants a specific pinned Chromium build (`PUPPETEER_EXECUTABLE_PATH`/Puppeteer's own auto-download); on at least one real dev machine the auto-download's ~157MB fetch couldn't finish inside the export subprocess's own 300s timeout, so it restarted from zero on every single render and never once succeeded. Because every render-based check in this codebase (`_check_smart_slide_layout`, the e& footer check, the standard-mode canvas-overflow check) is deliberately fail-open on any render/infra exception — see the reasoning in the codebase-audit section — this doesn't surface as an error at all: generation "succeeds" normally, decks look fine, and the only trace is an `ERROR ... slide_layout_check_failed` log line per slide, easy to miss. **Symptom to watch for**: if overflow/squeeze bugs that should be caught (scale-to-fit not kicking in, obviously-too-tall content shipping unflagged) are getting through, suspect this before suspecting the check's own logic. Fix: `npx @puppeteer/browsers install chrome@<version the bundle wants>` once (it will need the exact version the bundle's own error/log names, not just "a recent Chrome"), then set `PUPPETEER_EXECUTABLE_PATH` in `servers/fastapi/.env` to the extracted binary's path. Confirm it actually worked by watching render time drop to ~1-4s (a stuck download makes every render take the full 300s timeout) — don't just trust that the command exited without error.

**There are two separate, independent callers of that bundle — know which one a given export actually went through before assuming either side's export code ran.** `services/export_task_service.py` (FastAPI) is used by API-style endpoints that generate-and-export in one request (`presentation.py`'s `/edit`, `/derive`, and the main generate flow, all calling `utils/export_utils.py::export_presentation()`). But the interactive **"Export PPTX"/"Export PDF" button in the presentation editor** (`PresentationHeader.tsx`) calls a completely different, parallel implementation: the Next.js route `app/api/export-presentation/route.ts` → `lib/run-bundled-presentation-export.ts`, which spawns the bundle itself from the Next.js process and never touches FastAPI at all. Both build an equivalent `{type:"export", url, format}` task JSON and point at the same `/pdf-maker` URL, but they are two separate, duplicated code paths — a fix or feature added to one (e.g. a query param threaded through the export URL) does nothing for the other unless added to both. This was discovered the hard way: the native-chart-export feature below was originally wired only into `export_utils.py` and silently never ran for real interactive exports, since those never go through it. If FastAPI logs show zero export activity for an export you just triggered from the editor UI, this is why — check the Next.js terminal/`[bundled-export]`-prefixed logs instead.

That downloaded bundle (`presentation-export/`, gitignored — **never edit it directly**, changes vanish on the next `npm install`/re-sync) is also **patched**, not used verbatim: `scripts/sync-presentation-export.cjs`'s `KNOWN_BUNDLE_PATCHES` applies small string-replacement fixes for known upstream bugs after every download (currently one: a fully-rounded non-square element, like a pill badge, was misclassified as a circle and exported as a squashed oval in PPTX — patched in the JS shape-classification logic). Patches are pinned to the exact `presentationExportVersion` in `package.json` and skip themselves with a console warning (not a hard failure) if the bundle's code no longer matches, so bumping that version needs each patch re-verified against the new bundle before it'll take effect again. Two other real PPTX export bugs were found and are **not** fixable from this repo: a text run's own inline color/font-size (e.g. a bold red number sitting inline next to smaller plain text) gets flattened to the surrounding text's style on export, and some decorative elements land off-center. Both trace into `presentation-export/py/convert-*`, a compiled PyInstaller Python binary with no available source — fixing them needs either the upstream `presenton/presenton-export` source or reverse-engineering the binary, both out of reach here. The practical workaround is avoiding the triggering pattern in generated HTML (e.g. giving an emphasized number its own block instead of an inline span mixed with differently-styled text) rather than trying to fix the converter.

**Electron was removed** from this fork in commit `5d4665f` ("Removed electron," ~Aug 22). Vestiges remain and are currently broken/stale, not yet cleaned up:
- `Dockerfile` and `Dockerfile.dev` both still `COPY electron/resources/...` — a from-scratch Docker build currently fails at that step.
- `.github/workflows/electron-linux-ubuntu22.yml` still tries to build the removed `electron/` directory.
- Frontend Electron-detection code (`isElectronRuntime()`, `window.electron?.exportPresentation`) still exists throughout the Next.js app but is now vestigial — nothing ever sets `window.electron`.

## Route reachability map (Next.js)

This app carries a lot of well-built, upstream presenton.ai code that the live e& product no longer routes to. Twice in one session an assistant gave wrong answers about the live UI by finding and trusting genuinely good code that turned out to be unreachable. **Before trusting any `page.tsx` you find by name/keyword search, grep the entire `app/` + `components/` tree for that route's literal path string (`"/routename"`, `` `/routename` ``) used in `Link href=`, `router.push/replace`, or `redirect`.** If the only hits are inside the route's own subtree, it's very likely orphaned.

**Live, reachable routes:**
- `/` (`app/page.tsx`) — the real app home (`DashboardShell` → `DashboardPage`). Everything else is reached from here or from deeper pages.
- `/generate` → redirects to `/generation`. `/dashboard` → redirects to `/`. Both are legacy-URL shims kept for old links/buttons, not meaningfully different pages.
- `/generation` (`GenerationPageClient.tsx`) — the **primary** generation entry, linked from the dashboard's "Create with AI" button. Three-button UI: Outline / Generate Standard / Generate e& deck (see the button-label note above — none of those labels match the backend `standard`/`smart` split cleanly).
- `/upload` (`UploadPage.tsx`) — a **second, independent** generation entry with a real Standard/Smart `GenerationModeDialog.tsx` toggle. Not linked from the dashboard's main CTA, but reachable from: first-time onboarding's "Go to Upload" button, the outline page's empty state, the community page's "New presentation"/"Use this design" actions, and the presentation editor's error-recovery fallback. Two files inside its `components/` folder are true dead leftovers with zero importers: `LanguageSelector.tsx`, `NumberOfSlide.tsx`, plus an unused `styles/main.module.css`.
- `/outline`, `/presentation` (needs `?id=`), `/custom-template`, `/template-preview`, `/community`, `/theme`, `/settings` — all confirmed live, standard parts of the generation/editing pipeline and dashboard.
- `/templates` — reachable, but the two persistent "Templates" sidebar/nav links to it are intentionally disabled no-op buttons (`onClick={() => undefined}`); the page is still landed on programmatically after custom-template creation finishes.
- `/admin` (`AdminPanel`) — has zero in-app `Link`/`router.push` anywhere, reachable only by typing the URL directly. Not dead code, though: the same `AdminPanel` component is actively used, embedded as a tab inside `/settings`. If asked "where's the admin panel," point at the `/settings` tab, not this standalone route.
- `(export)/pdf-maker` — live, but only as a **headless render target** for the export pipeline (`lib/run-bundled-presentation-export.ts` launches Puppeteer against it). No user-facing link points here; don't treat the absence of one as meaning it's dead.

**Confirmed dead/orphaned — inherited from upstream, do not treat as representative of the live app:**
- `app/frontend/` (`page.tsx` + `index.tsx`) — a full standalone alternate dashboard/generation prototype (renders the upstream Presenton onboarding wizard via `components/Home.tsx`, or an entirely separate 700-line prototype in `index.tsx` that isn't even imported by its own `page.tsx`). Zero inbound links anywhere in the app; its "Generate" action also hardcodes `http://127.0.0.1:8000`, bypassing the Next.js proxy entirely, which wouldn't work in any real deployment anyway.
- `/documents-preview` (`DocumentPreviewPage.tsx`) — fully wired (calls `router.replace("/outline")` internally) but nothing links into it anymore; only referenced defensively in `Header.tsx`'s back-button path-matching array.
- `components/DashboardNav.tsx` — an alternate sidebar variant, never imported anywhere.
- Dead Next.js API routes (zero callers found in either the Next.js frontend or the FastAPI backend): `api/github-stars`, `api/has-required-key`, `api/templates` (the plain, non-`v1` one — the directory it reads, `app/presentation-templates/`, doesn't even exist on disk), `api/upload-image` (real image uploads go through `api/v1/ppt/images/upload` on FastAPI instead).

## Codebase audit (this session) — what's fixed, what's deferred, and why

A full-codebase review (two parallel Explore-agent passes over `servers/fastapi` and `servers/nextjs`, plus direct verification against the code and the live SQLite DB) found a cluster of real bugs, several of them silent. Four were fixed and verified live this session; the rest are deferred with reasons, not dropped. Full detailed writeup of every finding — including ones not listed below — sits in the plan file `abstract-tickling-teapot.md` if it's still around; this section is the durable record.

**Fixed and verified this session:**

- **Native chart export was completely inert whenever auth is enabled — fixed.** The chart-capture call from the export page uses `navigator.sendBeacon` (required — see the `networkidle0` note below), which cannot attach the session cookie. `api/middlewares.py`'s `SessionAuthMiddleware` requires auth for everything under `/api/`, and the chart-capture endpoint was never exempted, so the request was rejected 401 before it ever reached the handler — silently, since the capture pipeline is deliberately best-effort and logs at INFO, not ERROR. Every chart in every export stayed a flattened image in exactly the deployment mode (`DISABLE_AUTH` unset) this project's own README says is correct for anything beyond local dev. It worked in every session that built and tested this feature only because `DISABLE_AUTH` happened to be on. Fixed by adding `/api/v1/ppt/presentation/export/chart-capture` to `SessionAuthMiddleware._PUBLIC_AUTH_PATHS`; the token is a server-minted `uuid4` (122 bits) and `chart_capture_store._capture_path` already sanitizes it against path traversal, so the exemption doesn't weaken anything — it just matches what the endpoint's own docstrings already claimed. Since the endpoint becomes reachable with no session, also added abuse caps that didn't exist before: `charts` is capped at 200 items (pydantic `max_length`; measured max across every slide in this app's own database is 2) and the serialized payload at 2MB (`413` if exceeded). **Verified live**, not just unit-tested: started FastAPI with `DISABLE_AUTH=false` (overriding `.env`, which sets it — `load_dotenv(..., override=False)` means an exported shell value wins), confirmed a neighboring endpoint (`/upgrade-charts`) correctly 428'd with no session while `/chart-capture` returned 200 and the capture file actually landed on disk; then confirmed the 200-item payload is accepted and 201 is rejected 422. Tests: `tests/unit/test_session_auth_middleware.py` (path-exemption + full-dispatch-level proof), `tests/unit/test_chart_capture_endpoint.py` (cap tests).
- **A chart that failed to convert could disappear from the exported deck entirely — fixed.** `_replace_picture_with_native_chart` in `services/pptx_native_chart_service.py` removed the flattened-image picture from the slide's shape tree *before* calling `add_chart()`. If `add_chart()` raised for any reason (a malformed category/series shape, say), the `except` returned `False` without restoring the picture — so a deck where 8 of 9 charts converted fine and one hit an edge case saved successfully, with an empty hole where that one chart used to be, and a log line ("failed to build native chart for one slide") that reads as "the picture is still there." Fixed by wrapping `add_chart()` in its own try/except that re-inserts the original picture element at its original tree position before re-raising, so the documented contract ("upgrade fails → chart stays a flattened image") is actually true in this case. Test: `tests/unit/test_pptx_native_chart_service.py::test_failed_add_chart_leaves_the_original_picture_in_place`, which forces `add_chart` to raise and asserts the exact original picture element is back in its exact original tree position.
- **Export failures showed a generic toast that discarded the server's real error message — fixed.** `app/api/export-presentation/route.ts` already returns a genuinely useful message on failure (`{error, success:false}` — including things like "Cannot find module 'sharp'" or "presentation-export runtime is not available"), but `PresentationHeader.tsx`'s `handleExportPptx`/`handleExportPdf` threw a fixed `new Error("Failed to export PPTX")` on any non-OK response instead of reading the body, so every failure mode looked identical to the user. This is backlog item 2 above. Fixed by routing both handlers through `ApiResponseHandler.handleResponse` (`app/(presentation-generator)/services/api/api-error-handler.ts`) — the app's existing shared parser for exactly this response shape, already used elsewhere — and showing `error.message` in the failure toast instead of the fixed string.
- **Exporting could silently ship a just-made edit's old content — fixed.** `useAutoSave` debounces writes (2s in the editor), but `PdfMakerPage.tsx` reads the presentation straight from the database for export, not from the editor's live Redux state — so editing a heading and immediately clicking Export could produce a file with the pre-edit text, with no warning either way. Fixed by adding `flushSave()` to `useAutoSave.tsx`: it cancels the pending debounce timer, waits out any save already in flight (tracked via a single `activeSaveRef` that every internal trigger point — the debounce timer, the trailing-pending-change retry, and this new explicit flush — now routes through, so "a save is running" is never ambiguous), then runs one more pass of the same diff-and-save-if-needed logic `saveLatest` always uses, which costs nothing when there's genuinely nothing new (the diff check no-ops immediately) and still catches a change that arrived while the earlier save was running. Threaded through `PresentationPage.tsx` → `PresentationHeader.tsx` as `flushAutoSave`, awaited at the top of both export handlers before the request is built, for both the electron and browser_api runtimes. **Not live-verified this session** (would need manual editor interaction) — typechecked clean and reuses `saveLatest`'s existing, unmodified diffing logic, but worth a manual check (edit a heading, export within 2s, confirm the file has the edit) before relying on it for a demo.

**Deliberately not fixed this session — targets confirmed dead code.** An `IndexError` crash was found in `presentation.py`'s `generate_presentation_handler` (~line 2729: a loop guard checks `index >= total_outlines`, which can never be true inside `range(total_outlines)` — it should check the *list's own length*, since `generate_structured_with_schema_retries` can return a schema-invalid, too-short list after exhausting its retries). Traced its reachability before touching it: it's reachable only via `POST /generate` and `POST /generate/async`, and grepping the entire `servers/nextjs` tree for both literal paths found zero callers — the live app's real generation flow is `POST /prepare` + `GET /stream/{id}`, which already validates this correctly 600 lines away in the same file (`stream_presentation`, checks both length and negative indices). Fixing the unreachable copy would be correct but would fix nothing a user can ever hit; not worth the diff. Same reasoning applies to the debug `print()` calls found nearby (`presentation.py:2452, 2689-2690, 2809`) — same dead function, same non-decision. If `/generate`/`/generate/async` are ever exposed as a real external API, revisit both together.

**Deferred, not dead — real bugs, larger or needing a live run to verify safely:**

- **Smart-mode charts intermittently render blank in the live editor while a deck is still streaming — root-caused this session, not yet fixed.** See the updated diagnosis below (was backlog item 5); both previously-listed suspects are now confirmed *not* the cause.
- **A fit-scale-to-shrink wrapper (added last session to stop Smart slides from clipping) miscomputes geometry on slides whose root `<section>` has its own padding** (`_slide_html_scaled_to_fit` in `generate_smart_presentation.py`) — with `box-sizing:border-box`, the wrapper's hardcoded `1280×720` no longer matches the padded content box, so the transform origin shifts off-center and any `absolute`/`h-full` descendant re-anchors against the wrong rectangle. Measured against the live DB: 26.4% of stored smart slides have root padding (0% have root `flex`/`grid`, so padding is the only case that matters), and the bug is currently **latent** — every slide scaled so far happens to be unpadded, purely by chance. Fix shape: move the root's padding classes onto the wrapper instead of leaving them on the section. Needs a real render of a padded, overflowing slide to confirm the fix before it ships, not just a unit test.
- **The Smart-generation retry loop treats infrastructure failures (a 429, a dropped connection) as if the model's HTML were invalid** — the outer exception handler in `generate_smart_presentation.py`'s retry loop doesn't distinguish an LLM/network error from a real validation failure, so a rate limit gets fed into the next prompt as "correct this before returning the next slide," and the loop retries immediately with no backoff, up to 8× per generation.
- **No concurrency cap on Chromium spawns** — `export_task_service.py`'s `_run_task_locked` has a name that promises a lock that doesn't exist (`grep Semaphore` across the backend: zero hits). Every Smart slide's layout check spawns a fresh Chromium; under real concurrent load this is the most likely way the server falls over. Needs a real `asyncio.Semaphore` plus a decision on the concurrency limit, not something to guess at without load-testing.

   **A real false-positive found and fixed during calibration, worth remembering.** The first implementation stripped *both* `overflow-hidden` and the fixed `h-[720px]` height (switching to `h-auto`) before re-rendering, on the theory that this would let natural content height show cleanly. Tested against 10 real slides from a deck already verified fully clean via live browser screenshots (the font-size-fix testing deck) — and one slide "measured" as overflowing by **390px**, wildly wrong. Root cause: Tailwind's `h-full`/flex-column/grid-stretch sizing throughout a slide's internal layout all depend on that 720px box being a *definite* CSS height — per spec, a percentage height (`h-full` = `height:100%`) against an `auto`-height ancestor doesn't resolve the way authors expect, so switching the root to `h-auto` doesn't just "unclip" the box, it changes how *every descendant's* height computes, producing bogus, wildly inflated measurements especially on slides with nested CSS Grid (`grid-cols-[Npx_1fr]`) + flex-column combinations (common in this app's generated layouts).    **Follow-up: this same check's own bug then broke a real e& generation — root-caused from real backend logs and fixed, including the actual pie/donut content issue it was correctly flagging.** User reported the 14-slide "Chart Stress Test" prompt (see the stress-test prompt below) failing twice via "Generate e& deck," both times stalling around slide 8-10 and eventually erroring "failed to generate the complete Smart presentation after retries; N valid slides were retained." Diagnosed from real pasted backend logs (not speculation): `[smart-generation] attempt=5/8 accepted_slides=6` stayed at 6 through `attempt=6/8` — stuck on slide 7 (the pie chart, "Traffic source breakdown"), being rejected by this exact check's own error text ("The Smart slide's own content is taller than the fixed 720px canvas..."), confirming the render itself succeeded and a *genuine* overflow was detected, not an infra failure.

   Two Explore agents plus direct code verification found two real, independent issues:
   - **The root cause of the actual failure: e&'s content budget is measurably too tight for a pie/donut chart, and nothing told the model that.** e& reserves only `y=48` to `y=630` (582px) for content, vs. plain Standard mode's ~640px. Pulled the existing working Standard-mode pie slide from `app_data/fastapi.db` and measured its real layout: header + `h-[470px]` chart card + gaps + footer totals 711 of 720px available — already a near-zero-margin fit *before* accounting for e&'s smaller budget and its own established pattern of a larger `text-[43px]` headline (vs. Standard's `text-[36px]`, required by e&'s "preserve visual continuity with earlier accepted slides" continuation instruction). That left only ~410-430px for the chart card — 40-60px short of what a legible pie/donut needs, since (unlike bar/line/area) a pie/donut has to stay close to square to remain legible. `CONTENT DESIGN DIRECTION` in `smart_brand_templates.py` already had specific, named overflow-pattern warnings for other known-risky compositions (a full-height side rail, shared card heights) but none for chart-dominant slides. Fixed by adding a new bullet (both to the e&-specific prompt and a lighter version in the general `SMART_OVERFLOW_PREVENTION_PROMPT`) explicitly telling the model a pie/donut chart card needs ~380-420px budgeted *first*, with the header/support content sized to fit around it — not the other way around.
   - **A separate, real bug found while investigating (not what caused this specific failure, but a genuine defense-in-depth fix): infra failures were misclassified as validation failures.** Both `_check_smart_slide_canvas_overflow` and `_check_smart_slide_eand_footer_safe_area` wrapped their render call in `except HTTPException: raise / except Exception: ...return (fail open)` — but `EXPORT_TASK_SERVICE.render_html_to_image` itself raises `HTTPException(500, ...)` on its own 300s timeout or a subprocess crash, so a genuine infra hiccup took the *same* `except HTTPException: raise` path as a real 400 validation failure, aborting the whole attempt and feeding the model an uncorrectable `retry_error` like `"Export task failed. returncode=..."`. Fixed by removing the special-cased re-raise entirely, so **any** exception from the render call (HTTPException included) now hits the fail-open branch; only this function's own post-render validation raise (which happens outside that try, after the render already succeeded) can propagate. Applied identically to both functions, which shared the exact same flaw.
   - Also made the overflow error message itself actionable: `_count_non_sentinel_pixels_below_canvas` already computed a full-resolution thresholded diff image, so extending it to also return `thresholded.getbbox()`'s deepest row (free, no extra render) let the raised message state a concrete "approximately Npx taller than the fixed 720px canvas" instead of generic "too tall" wording the model had no specific target to correct against.

   **Second follow-up: the prompt guidance alone was not enough, so the retry loop itself was made fault-tolerant.** After the above shipped, the same 14-slide e& deck failed again — this time the log showed the pie slide (slide 6) *accepted* with a 440x440 canvas (the guidance demonstrably worked there), but the next chart slide stalled at `attempt=5/8 accepted_slides=6` → `attempt=6/8 accepted_slides=6`, rejected at "approximately 219px taller than the fixed 720px canvas," and generation died again. **The structural problem was never really the prompt: one slide the model cannot get under the threshold consumes every remaining attempt and takes the entire deck down with it.** These render checks are *quality* gates, not correctness gates — a slide that overflows somewhat is vastly better for the user than no deck at all — but nothing in the loop expressed that. Fixed by tracking consecutive failures at the *same* slide position (`stalled_at_index`/`consecutive_stalls`, reset whenever any new slide is accepted, so it only ever triggers on a genuinely stuck position) and, past `SMART_MAX_CONSECUTIVE_SLIDE_FAILURES = 3`, waiving the render-based checks **for that one slide position only** (later slides in the same response are still fully checked) and logging a warning. Hard validity checks — malformed HTML, missing chart initializer, wrong slide type/count — are never waived. Regression test added, and confirmed to genuinely catch the bug: it **fails** when the threshold is disabled and passes with it, plus a companion test proving the waiver is scoped (a response that never yields any usable slide must still fail rather than silently returning a short deck). Also replaced a bare `print(messages)` in the retry loop with `LOGGER.debug` — it dumped the entire prompt (tens of KB, growing with every retry as accepted slide HTML is re-appended) to stdout, which made the backend logs nearly unreadable in exactly the situation where they matter most.

   **Generation-speed profiling (measured, not guessed) — and the one easy win it found.** Instrumented `generate_smart_presentation` to time LLM calls vs. render checks separately across real e& chart generations. Results were consistent across three runs: **LLM calls are ~85-90% of wall time, and the multiplier is retries** (87s/3 attempts on a success; 164s and 206s on 8-attempt failures). Render checks were ~1s each and ~10-16% of total. So micro-optimizing rendering can never fix a slow generation — the lever is not wasting LLM attempts, which is what the stall waiver above addresses. The one genuinely easy render win was real though: **e& slides were rendering the page twice per slide** — `_check_smart_slide_canvas_overflow` and `_check_smart_slide_eand_footer_safe_area` each spawned their own cold Chromium to measure the *same* rendered page. Consolidated into a single `_check_smart_slide_layout(html, *, check_eand_footer)` that renders once and checks two bands of the same image: past y=720 against the sentinel page colour (canvas overflow), and y=630-720 against white (e& footer intrusion, still inside the slide's own box so the comparison is unchanged). Benchmarked directly on a slide that passes both checks (so the old path didn't short-circuit): **2 renders / 1.86-2.08s → 1 render / 0.95-0.96s per e& slide, ~54% faster**, with non-e& unchanged at one render either way. The four now-dead functions and their 10 tests were deleted rather than left as a second implementation that could silently drift.

   **A profiling trap worth remembering: a dead backend makes every render look 10x slower.** The first profiling pass measured a rock-steady ~10.8s per render regardless of slide content — even for a slide containing nothing but `<p>hello</p>` — which looked exactly like a smoking-gun fixed timeout. It was an artifact: the FastAPI server had died mid-session, so the preview page's `<script src="http://127.0.0.1:8000/static/vendor/tailwindcss-browser-*.js">` 404'd. The export bundle's `waitForTailwindCdn` probe (`nnt` in `presentation-export/index.js`) detects Tailwind by the *presence of a script tag matching `/tailwind/i`* — which is still true when the fetch failed — then polls up to **10s** for a probe `<div class="hidden">` to compute `display:none`, which can never happen if the script never loaded. With the server up, Tailwind compiles `.hidden` in ~800ms and renders take ~0.95s. **Always confirm the backend is actually serving `/static/vendor/...` before and after any render benchmark** — a mid-run death silently inflates every number by ~10s and looks like a real finding. Regenerated the identical 14-slide e& prompt against the real running servers via direct API calls (`POST .../presentation/create` then `GET .../presentation/stream/{id}`), capturing the full backend log. This run's log showed the new fix actually firing three times with real, concrete numbers (`approximately 30px`/`222px`/`6px taller than the fixed 720px canvas`) — confirming the message-improvement fix is live — and, critically, **the generation completed successfully this time**: all 15 slides (title + 13 content + closing) persisted, including slide 7 (pie) and slide 8 (donut), within the same 8-attempt budget that previously exhausted itself without ever completing. Slide 7 still needed 2 retries before converging (real content-shape difficulty doesn't vanish entirely from prompt guidance alone), but recovered instead of permanently stalling. Inspected the actual generated pie slide HTML: the model used `text-[36px]` (down from the previous attempt's `43px`) and a `h-[430px]` chart card, matching the new guidance's recommended range almost exactly. Added regression tests for the exception-handling fix specifically (an `HTTPException(500)` from the render call must now fail open, for both checks — the previous test suite only covered a generic `RuntimeError`, which is exactly the gap that let this bug ship unnoticed) and for the new prompt guidance being present in both the general and e&-specific prompt output.
5. **Open: Smart-mode charts intermittently render blank in the live editor while a deck is still streaming — root cause now identified, fix not yet built.** Reported with a screenshot: during an e& generation, slides 3-4 appeared in both the sidebar thumbnails and the main canvas with their chart cards completely empty (border and card title present, no chart), then the charts "randomly showed up again" once slide 6 finished generating. Self-healing, so cosmetic rather than blocking, but real.

   **Both previously-listed suspects are now confirmed NOT the cause.** During streaming, `SlideContent.tsx`'s `canEditSlide` is `false` (gated on `isStreaming !== true`), so the main canvas renders `SmartHtmlSlide` (an iframe) — never `SmartHtmlEditor` — and `useSmartChartInjection` (the hook both suspects lived in) simply never runs at all in this scenario. The duplicate-`instanceId` theory is also impossible: both `SmartHtmlEditor.tsx` and `SmartHtmlSlide.tsx` append `Math.random().toString(36).slice(2)` to their instance ids, and the sidebar's iframe path never writes `data-smart-slide-instance` into the parent document to begin with.

   **Real cause: every visible Smart slide gets its own `srcDoc` iframe, and each one cold-loads ~490KB of render-blocking script before its inline chart-init code can run.** `SmartHtmlSlide.tsx`'s iframe `<head>` loads three classic (non-async) scripts — `tailwindcss-browser-4.3.3.js` (281KB), `chart-4.5.1.umd.min.js` (208KB), `chartjs-plugin-datalabels-2.2.0.min.js` (13KB) — and the slide's own generated HTML has an inline `new Chart(canvas, ...)` IIFE that runs immediately against the global `Chart`, which doesn't exist until that script finishes parsing and executing. There is **no viewport culling for Smart slides on the main canvas** (`enableViewportCulling` is accepted by `SlideScale` but only ever forwarded to the TemplateV2 branch, `PresentationRender.tsx`, never to the `SmartHtmlSlide` branch), so a 14-slide deck holds up to ~18 live iframes (main canvas + thumbnails) each running an independent Tailwind JIT + Chart.js instance. When a reasoning model emits a fast burst of several slides at once (the deck's own documented streaming behavior), multiple iframes mount in the same frame and compete for the same render thread — the ones still mid-parse show their card border/title (plain HTML, renders fine) with an empty canvas, then "heal" once their script catches up. Matches the report exactly, including the self-healing.

   **Cheapest next step, not yet done:** forward `enableViewportCulling` into the Smart-slide branch of `PresentationRender.tsx`, and warm `loadChartBrowserRuntime()` on the presentation page during streaming rather than only from inside `useSmartChartInjection` (which never runs during streaming, per above). Re-measure before considering the larger structural fix (one shared renderer instead of one iframe per slide).
